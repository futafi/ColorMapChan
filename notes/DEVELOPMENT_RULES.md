# 開発ルール

## Git管理ルール

### バージョン管理
- **Semantic Versioning**: x.y.z形式で管理
  - x: メジャーバージョン（互換性なし変更）
  - y: マイナーバージョン（機能追加）
  - z: パッチバージョン（バグ修正）

### コミットルール
- **細かい単位でのコミット**: 機能単位・修正単位で小刻みにコミット
- **コミットメッセージ形式**: `[Phase X.Y] 実装内容の簡潔な説明`
  - 例: `[Phase 1.1] Add main.py with GUI/CLI switching`
  - 例: `[Phase 1.2] Implement PlainCSV data loader`
  - 例: `[Phase 1.5] Add GitHub Actions for pytest`

### ブランチ戦略
- **メインブランチ**: `v2` ブランチ（作り直しプロジェクト用）
- **開発**: v2ブランチとその派生ブランチを使用
- **頻繁なpush**: 実装状況を確認するため細かくpush

## 実装ルール

### 優先順位
1. **動作することが最優先**: 完璧性より動作性
2. **テスト可能性確保**: CI/CDで自動テスト必須
3. **シンプルな実装**: 個人用途のため複雑性を避ける
4. **exe生成可能性**: PyInstallerでのビルド成功必須

### コード品質
- **pytest**: 全てのコア機能にテスト必須
- **GitHub Actions**: 自動テスト・ビルド必須
- **エラーハンドリング**: 基本的なエラー処理のみ（過度な複雑化避ける）

### 開発フロー
1. Phase計画に従った段階的実装
2. 各機能実装後に即座にコミット
3. GitHub Actionsでの自動テスト確認
4. exe動作確認（重要なマイルストーン時）
5. 次のPhaseに進行

## プロジェクト特性

### 個人プロジェクト
- **非公開**: コード品質より実用性優先
- **シンプル重視**: 過度な設計パターン不要
- **動作優先**: バグ修正・機能追加のスピード重視

### Windows配布対象
- **exe形式**: PyInstallerでのシングルバイナリ
- **GUI操作**: tkinter素デザインで十分
- **依存関係最小化**: requirements.txtの簡潔性

## CI/CD要件

### 必須チェック
- **pytest全通過**: コア機能のテスト必須
- **PyInstaller成功**: exe生成可能性確認
- **依存関係解決**: requirements.txt正確性

### 自動化対象
- **テスト実行**: プルリクエスト・プッシュ時
- **exe生成**: リリースタグ時またはメインブランチ更新時
- **成果物配布**: GitHub Releasesでの自動配布
